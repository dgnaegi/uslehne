# uslehne — Architecture Overview

## System Overview

```
Browser
  │  HTTP (REST JSON)
  ▼
React SPA (Vite)          ← served as static files on Scalingo
  │  /api/* proxy → :3001
  ▼
Express API (Node.js)     ← Scalingo web dyno
  │  Prisma ORM
  ▼
PostgreSQL                ← Scalingo PostgreSQL addon
```

In production both apps are separate Scalingo applications deployed via `git subtree push`. In development Vite proxies all `/api` requests to the backend on `:3001`.

---

## Data Model (high level)

| Entity | Purpose |
|---|---|
| `User` | Account, kudos balance, rating aggregate |
| `Address` | Pickup locations belonging to a user |
| `Offer` | Item listed for lending or giving; has one image |
| `Transaction` | Lifecycle of a request: PENDING → ACCEPTED → RETURNED/COMPLETED |
| `Rating` | 1–5 stars left by the owner after a transaction |
| `Invite` | Single-use invite codes; grants a kudos bonus on registration |
| `KudoLedger` | Append-only ledger of every kudos credit/debit |

Offers have two types — **LEND** (temporary, returned) and **GIVE** (permanent). The transaction status machine tracks the full lifecycle of both.

---

## Authentication

JWT-based. The backend signs a short-lived token on `/api/v1/auth/login`; the frontend stores it and sends it as a `Bearer` header. `/api/v1/auth/me` validates the token and returns the current user. No sessions, no cookies.

---

## Kudos Economy

Kudos are an internal currency:

- Registering with an invite code → bonus credited to the new user
- Borrowing an item → kudos debited from requester, credited to owner
- Receiving a give → small debit; giving earns kudos
- Every credit/debit is written to `KudoLedger` for a full audit trail

The balance lives on `User.kudosBalance` (denormalised for fast reads); the ledger is the source of truth.

## Image Storage

Image storage is environment-driven and swapped at boot via a factory function (`backend/src/storage/imageStorage.ts`):

| Mode | When active | How it works |
|---|---|---|
| **Base64** | `IMAGE_STORAGE=base64` or S3 env vars absent | Image is stored as a base64 data URL directly in the database. Simple, no infra required — used locally. |
| **S3-compatible** | All S3 env vars present | On upload the backend decodes the base64 payload, validates MIME type and size (≤ 2 MB), then PUTs the binary to an S3-compatible bucket with `public-read` ACL. The database stores only the object key; the URL is reconstructed at read time. |

Both modes share the same `ImageStorage` interface so the rest of the codebase is unaware of which backend is active. Legacy rows that contain a data URL are passed through transparently by the S3 implementation.

**Allowed types:** JPEG, PNG, WebP — max 2 MB.

---

## Invite-only Access

Registration requires a valid invite code. Each code is single-use and generated by an existing user. This keeps the community small and trusted, and seeds the new user's kudos balance with the bonus attached to the invite.

---

## Deployment

Both apps are deployed independently to Scalingo (European PaaS, GDPR-friendly):

```bash
# Backend
git subtree push --prefix backend scalingo-backend main
scalingo --app uslehne run npm run db:migrate   # after schema changes

# Frontend
git subtree push --prefix frontend scalingo-frontend main
```

Database migrations are run manually after each backend deploy that introduces schema changes.
